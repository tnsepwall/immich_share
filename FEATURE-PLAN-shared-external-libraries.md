# Feature Plan: Shared External Libraries

**Goal:** Let a user share their external library with other users on the same Immich server. Sharing is opt-in and controlled by the library owner: nothing is shared until the owner explicitly adds users, assigns each user a Viewer or Editor role, and the owner can change the role or remove the user at any time. Viewers can view, download, and add visible assets to their own albums. Editors can additionally help curate visible assets by correcting descriptive metadata/date/location (which controls timeline sorting) and labeling faces. Neither role can delete assets, change library settings, change asset visibility, run maintenance jobs, or access archived, locked, or trashed assets.

**Target:** Immich v3.0.2 source at this repo root (pnpm monorepo: `server` NestJS + Kysely/Postgres, `web` SvelteKit, SDK generated from OpenAPI).

**Scope:** Server + Web. Mobile app is explicitly out of scope for v1 (see "Out of scope"). Shared-library assets appear in a dedicated browse view, not merged into the recipient's main timeline (that's a listed follow-up).

## 2. Design decisions (locked in — don't re-litigate)

1. **New join table `library_user`** mirrors `album_user` and includes a `role` column using a new `LibraryUserRole` enum with `viewer` and `editor`. The library owner is not represented by an owner row; ownership remains `library.ownerId`. Sharing is "enabled" simply by having rows; **no extra `isShared` boolean** on `library`. Empty list = private (default), and new shares default to Viewer.
2. **Owner-managed.** Share management endpoints require the requester to be the library owner (admins can also manage — they can already do everything else to libraries). A shared user may remove **themselves** (leave a share).
3. **Role-scoped recipient access.** Both roles reuse the partner read semantics for `AssetRead`/`AssetView`/`AssetDownload`. They do **not** receive global `AssetShare`: that permission also enables shared-link creation and would turn the owner's revocable library share into a durable secondary grant. Adding an asset to the recipient's own album instead uses the dedicated, provenance-aware `LibraryAssetAddToAlbum` path below. Editors get narrowly scoped library-curation endpoints; do **not** add shared-library editors to the global `Permission.AssetUpdate`, `PersonUpdate`, `FaceUpdate`, or `AssetDelete` unions because those permissions are reused by unrelated operations such as stacks, arbitrary metadata keys, live-photo linking, person merges, and maintenance jobs.
   - **Viewer:** browse/open/download visible assets and add them to their own albums.
   - **Editor — asset curation allowlist:** change `description`, `dateTimeOriginal`, `dateTimeRelative`, `timeZone`, `latitude`/`longitude`, and `rating` for non-deleted `Timeline` assets in this library. Date changes provide the requested sorting/ordering workflow. V1 editor writes are database-only via the transactional metadata primitive in **Step 5b**: they update `asset_exif` **and** the asset timeline columns together, add extraction locks but never sidecar-pending state, and never queue `SidecarWrite`, so an editor never creates or changes files beside the external originals. "Just don't queue the job" is NOT sufficient — see Step 5b for the two failure modes this must close.
   - **Editor — face-labeling allowlist:** list faces on visible assets in this library; list people represented by those faces; create a person owned by the library owner while atomically assigning at least one library face; reassign library faces to an eligible person; add a manual face box to a visible library asset; and change the `name` of a person only when all of that person's non-deleted faces belong to this library.
   - **Always owner-only:** `isFavorite`, visibility/archive/lock/trash, duplicate grouping, stacks, live-photo linking, arbitrary asset metadata keys, tags owned by another user, ML/thumbnail/transcode jobs, sidecar/file writes, person birth date/hidden/favorite/color/feature-photo changes, person merge/delete, face delete, asset delete, library scan/configuration, and any edit involving an asset or face outside this library.
   - Person thumbnails returned to editors must be derived from a face on an accessible asset in this library; never reuse a person's global feature thumbnail if it comes from an unshared asset.
4. **Browse via a dedicated timeline filtered by `libraryId`**, authorized by a new `Permission.LibraryRead` object-access rule (owner ∪ shared). Not merged into the recipient's home timeline in v1.
   - **Stacks are disabled for recipients in v1.** `StackRead` is owner-only (`server/src/utils/access.ts` ~line 313) so the viewer's `getStack` call would 400, and the `withStacked` lateral join counts/collapses stack members without a library boundary (`asset.repository.ts` ~line 869) — if the stack primary lives outside the shared library, in-library members would silently disappear from the bucket. Therefore: force `withStacked` off for non-owner library requests (Step 10), redact `stackId`/`stack` from recipient asset responses (Step 7), and do not render stack UI on the recipient browse route (Step 13). A library-scoped stack endpoint is a follow-up.
   - **Live photos:** expose `livePhotoVideoId` to recipients only when the motion asset passes the same shared-library access check. Motion parts created by `applyMotionPhotos` inherit the still's `libraryId`, so in-library playback works via the `Hidden`-visibility allowance; redact the field in the recipient mapping if the motion asset's `libraryId` differs (cross-library same-owner links are possible via live-photo linking).
5. **Recipients never see server filesystem paths.** Any DTO returned to non-admin/non-owner users must omit `importPaths`, `exclusionPatterns`, asset `originalPath`, sidecar paths, and derived-file paths. This applies to both Viewer and Editor responses, including the normal asset viewer/detail flow.
6. **Follow codebase conventions exactly**: zod DTOs with `.meta({id})`, `Endpoint`/`HistoryBuilder` decorators (new endpoints: `new HistoryBuilder().added('v3')` — copy from another v3-added endpoint), audit table + delete trigger like `album_user`, `createId/updateId` columns, `@GenerateSql` + snapshot regen.

### Derived album/link access — v1 policy

V1 uses a **library-authoritative** policy. Today album and shared-link membership are independent `AssetRead/View/Download` grants, so deleting `library_user` alone would not revoke them and album/shared-link access does not enforce Archive/Locked visibility. Implement all of the following rather than relying on the existing access union:

- Add nullable `sourceLibraryId` to `album_asset`, with a foreign key to `library.id` using `ON DELETE CASCADE` and an index. Existing/ordinary album entries have `NULL`; an entry added through `LibraryAssetAddToAlbum` stores the asset's exact library id.
- Permit this path only for an album owned by the recipient, not an album merely shared with them. At read/view/download time, an `album_asset` row with `sourceLibraryId` grants access only when the requester is the external-library owner or still has an active Viewer/Editor `library_user` row, the library is active, the asset still belongs to that library, and the asset is non-deleted `Timeline` visibility. This also prevents a recipient from laundering access by sharing their album with a third party.
- Keep `AssetShare` unchanged for external-library recipients. Therefore shared-link creation from this access source is denied in v1. If the requester independently has owner/partner `AssetShare`, that existing path may create the normal durable link or album entry without `sourceLibraryId`.
- On library-share removal, Archive/Lock, or library deletion, the provenance-bearing album entry no longer grants access. Removing the library may cascade-delete such album references; removing one `library_user` row leaves the album row for other authorized viewers but makes it inaccessible to that user.

**Enforcement must cover every `album_asset` read surface, not just `checkAlbumAccess`.** Amending `AssetAccess.checkAlbumAccess` alone is insufficient: album-scoped queries authorize the *album id* up front and then enumerate `album_asset` directly with no per-asset check. Build ONE reusable requester-aware predicate (e.g. `withAlbumAssetProvenance(qb, userId | null)` in `server/src/utils/database.ts`: keep `sourceLibraryId is null` rows; keep non-null rows only when `userId` is the source library's owner or holds an active `library_user` row, the library and its owner are non-deleted, `asset.libraryId = album_asset.sourceLibraryId`, and the asset is non-deleted `Timeline`) and apply it to every surface below. `grep -rn album_asset server/src` and disposition **every** hit in the PR description; the known read surfaces are:

- Timeline album queries: `asset.repository.ts` `getTimeBuckets` (~line 768) and `getTimeBucket` (~line 856) `albumId` branches.
- `DownloadRepository.downloadAlbumId` (`download.repository.ts` ~line 27).
- `MapRepository.getAlbumMapMarkers` (`map.repository.ts` ~line 73).
- Album responses/aggregations in `album.repository.ts`: asset counts / start-end dates / thumbnail metadata (~lines 65, 109–181) and any album asset listing.
- `shared-link.repository.ts` (~line 82) — see the shared-link rule below.
- `access.repository.ts` album checks (~lines 151, 240) — the `checkAlbumAccess` change already planned.
- `server/src/utils/database.ts` `withAlbums`-style helpers (~line 257) when they feed non-owner responses.
- Activity and search paths that filter by album (verify via the grep; activity access flows through album access checks but confirm no direct join).

**Shared links (public, unauthenticated) must never expose provenance rows.** Album shared-link creation requires only `AlbumShare` on the album id (`shared-link.service.ts` ~line 68) and link reads have no authenticated requester, so filtering alone is not enough — block at write time in both directions: (a) creating an album shared link fails with 400 when the album contains any `sourceLibraryId is not null` row; (b) `LibraryAssetAddToAlbum` insertion fails with 400 when the target album already has a shared link. Additionally apply the provenance predicate with `userId = null` (drop all non-null rows) in shared-link asset enumeration as defense in depth.

**Sync streams (required in v1 even though mobile UI is out of scope).** `AlbumAssetSync` backfill/updates (`sync.repository.ts` ~line 197) and the album-asset-EXIF equivalent stream every album asset to every album member with no per-asset check, and removing `library_user` generates no album-asset deletion audit — a recipient's (or third album member's) phone would cache library assets with no revocation path. Exclude `album_asset.sourceLibraryId is not null` rows from **all** album asset/EXIF upsert and backfill sync streams. Full mobile support (dedicated sync types + revocation deletes) stays a follow-up.

**Conflict precedence for the single `(albumId, assetId)` row.** NULL provenance is the stronger, durable grant: an ordinary `AssetShare` insertion must *upgrade* an existing non-null row to null (`ON CONFLICT (albumId, assetId) DO UPDATE SET "sourceLibraryId" = null`), while a `LibraryAssetAddToAlbum` insertion keeps `ON CONFLICT DO NOTHING` so it can never downgrade an existing durable row (`album.repository.ts#addAssetIds` ~line 289 currently uses DO NOTHING for everything — split the two paths).

**`copyAlbums` must carry provenance.** `album.repository.ts#copyAlbums` (~line 458) copies only `albumId` + the new asset id, which would silently convert a provenance row into a durable null grant; add `sourceLibraryId` to its insert-select column list.

If the product owner deliberately selects durable derived grants instead, remove this provenance design and rewrite the goal/security checklist to say removal revokes only direct library access. Do not mix the two policies.

- `server/src/utils/access.ts`, in `checkOtherAccess`:

    - `Permission.LibraryRead`: owner ∪ shared (`access.library.checkOwnerAccess` then `checkSharedAccess` on the difference).
    - `Permission.LibraryShare`: owner only.
    - `Permission.LibraryAssetAddToAlbum` treats its ids as **asset ids** and calls `checkSharedLibraryAlbumAddAccess`. Keep `Permission.AssetShare` unchanged so the shared-link service cannot consume this grant.
    - `Permission.LibraryAssetUpdate`, `Permission.LibraryPersonRead/Create/Update`, and `Permission.LibraryFaceCreate/Update` treat their ids as **library ids** and return owner ∪ Editor. The dedicated service then performs the asset/face/person scope check against the same route library id. Do not union any of these cases into the global asset/person/face permissions.

- Create `server/src/services/library-editor.service.ts` for the role-scoped curation operations and register it in `server/src/services/index.ts` (~line 53, alphabetical). Keep these checks out of the general `AssetService`/`PersonService` permission unions: those services use the same broad permissions for operations that editors must not receive. The editor service must first require curation access to the route library (owner ∪ Editor — **no admin branch in v1**: admin status does not bypass owner-only `AssetUpdate` today, so admins manage share lists but do not curate other users' assets; see open question 6), then validate every asset/face/person against that exact library.
- **Transactions:** every editor mutation (single and bulk metadata updates, create-person-and-assign, face reassignment, manual face, exclusive rename) runs its scope/role revalidation and its writes inside ONE Kysely transaction so a concurrent share revocation, role downgrade, archive/lock, or outside-library face addition cannot land between check and write — re-run the role and library-scope queries inside the transaction, not just before it. Bulk requests are atomic: if any id is outside the library or inaccessible, write nothing. Emit events and queue jobs only after commit.
- **Read-surface audit for the broadened `AssetRead/AssetView/AssetDownload` union:** adding `checkSharedLibraryAccess` to those three permissions opens every endpoint they guard, not just asset viewing. Grep `Permission.AssetRead|Permission.AssetView|Permission.AssetDownload` across `server/src/controllers` and `server/src/services` and produce an allowed/denied matrix in the PR description. Expected allowed: asset info (with Step 7 redaction), thumbnails/original/video playback, download. Must be checked and denied or consciously accepted: OCR text, asset metadata key-value endpoints, edit/audit history, smart-search seeding, and anything else found — an endpoint that must stay owner-only keeps its own narrower permission or gains an explicit owner check.
- **Step 5b — transactional database-only metadata primitive.** The plan's original "reuse `updateAll` minus the `SidecarWrite` queue" is not implementable safely, for two verified reasons: (1) `handleSidecarWrite` reads ALL of `lockedProperties`, writes them to the XMP sidecar, and unlocks them (`metadata.service.ts` ~lines 498–539) — and owners queue that job constantly (`AssetService.updateAll` ~line 180, tag/untag events ~lines 480–488), so an editor's "database-only" edit would be flushed to a file the next time the owner touches the asset; (2) date edits only reach the timeline through the `SidecarWrite → AssetExtractMetadata` job chain (`job.service.ts` ~line 111) that re-reads the XMP and rewrites `asset.localDateTime`/`asset.fileCreatedAt` (`metadata.service.ts` ~lines 372–377) — the editor path skips that chain, so the asset would never move buckets, and any later extraction resets those columns from disk regardless of `lockedProperties` (`lockedPropertiesBehavior: 'skip'` protects only `asset_exif` columns). - [ ] Timeline library path: non-owner cannot request archive/locked/trashed/favorite filters; visibility forced to Timeline; `withPartners` rejected.
- [ ] `SharedLibraryResponseDto`, `AssetResponseDto`, and anything reachable by recipients omit `importPaths`, `exclusionPatterns`, `originalPath`, sidecar paths, and other server filesystem paths.
- [ ] Share management restricted to owner/admin; self-removal allowed; no user enumeration beyond what the existing user search already exposes.
- [ ] Viewer has no write access. Editor writes use only dedicated library-scoped permissions/endpoints; global `AssetUpdate/AssetDelete`, person merge/delete, face delete, arbitrary metadata, jobs, and file/sidecar writes remain unavailable.
- [ ] Every editor operation checks the role and the exact route library, validates all ids atomically, and restricts assets to non-deleted `Timeline` visibility.
- [ ] Person/face responses and thumbnails are sourced only from this library; a person with any face outside the library cannot be renamed by an editor.
- [ ] Role downgrade/removal immediately revokes editor operations; tests cover an already-open editor page/API client.
- [ ] Provenance-bearing album rows require current library access at read time, cannot grant access to third-party album members, and stop granting after removal plus later Archive/Lock changes; ordinary null-provenance album rows retain existing behavior.
- [ ] Every `album_asset` read surface from the §2 enumeration applies the provenance predicate (`grep -rn album_asset server/src` dispositioned in the PR); album sync streams and shared-link enumeration exclude provenance rows; the two shared-link write-time guards are in place.
- [ ] `handleSidecarWrite` can never write or unlock an editor-locked property (only `sidecarWriteProperties`); metadata extraction cannot clobber locked exif values or the derived `asset.localDateTime`/`fileCreatedAt`.
- [ ] Editor mutations revalidate role + library scope inside the write transaction; events/jobs fire only after commit.
- [ ] The `AssetRead/View/Download` read-surface matrix is in the PR description; OCR, metadata key-value, and edit-history endpoints are explicitly dispositioned.
- [ ] Recipient responses redact `stackId`/`stack` and out-of-library `livePhotoVideoId`; recipients cannot reach `getStack`.
- [ ] API keys need `Permission.LibraryAssetAddToAlbum` explicitly for the album-add fallback; `AlbumAssetCreate` alone is insufficient.
- [ ] `AssetShare` is not broadened for shared libraries; shared-link creation remains denied and library-derived album insertion is limited to the recipient's own album.
- [ ] Recipient `assetCount` includes only non-deleted Timeline primary assets the recipient may browse and does not reveal archived/locked/trashed totals.
- [ ] `GET /libraries/mine|shared-with-me` return only the requester's data; admin routes unchanged (`admin: true` retained).
- [ ] SQL snapshot diffs reviewed (no accidental broadening of other queries).

## 7. Out of scope for v1 (follow-ups, note in PR description)

1. **Mobile app UI/sync types**: the Flutter app consumes the v3 sync stream; recipients' phones won't show shared libraries or their Viewer/Editor role until new `SyncEntityType`s (e.g. `LibraryUserV1` including `role`, shared-library asset/exif/person/face backfill types mirroring `PartnerAsset*` in `server/src/dtos/sync.dto.ts` + `sync.repository.ts`/`sync.service.ts`) are added. The `library_user_audit` table added here is the prerequisite, so the door is open. **Note:** the server-side exclusion of provenance rows from existing album sync streams (Step 8) is NOT deferred — without it, album membership would push library assets to every album member's phone with no revocation path, so that filter ships in v1.
2. Merging shared-library assets into the recipient's main timeline (`inTimeline`-style toggle per share, like partners).
3. Integration with the recipient's global search, map, main People page, and memories. The Editor-only library face-labeling panel is intentionally scoped to the shared-library route and does not merge the owner's people into the recipient's account-wide People UI.
4. Full/co-owner editing: changing visibility/favorites, tags owned by the library owner, stacks/live-photo relationships, duplicate management, ML/job controls, XMP/sidecar or original-file writes, person merge/delete, face delete, notifications/emails on share, and per-share expiry. V1 Editor is the narrower curation role defined above.

## 8. Build/dev quickstart for the implementer

- Requires Node 22+/pnpm (`mise install` sets toolchain), Docker for postgres.
- `pnpm install` at repo root.
- Dev DB for migration generation + medium tests: `docker compose -f docker/docker-compose.dev.yml up -d database` (check service name in that file).
- Server: `pnpm --filter immich run check` (types/lint), `pnpm --filter immich test`.
- SQL snapshots: `mise //:sql` after changing any `@GenerateSql` query.
- OpenAPI/SDK: `mise open-api` after server DTO/controller changes; then `pnpm --filter immich-web run check:code` (there is no plain `check` script in `web/package.json` — the scripts are `check:svelte`, `check:typescript`, `check:code`, `check:all`).
- End-to-end: `mise //e2e:test` after unit/medium coverage is green.
- Note: this checkout lives under a cloud-synced folder — if file-watcher/symlink issues or mysteriously hidden files appear, copy the tree to a non-synced local path or run builds/tests inside Docker before heavy work.

### Implementation order (do not build all at once)

Ship/review in four self-contained phases; each ends with its tests green:
1. **Direct sharing + safe read**: Steps 1–4 (minus album/exif schema extras if you want to split further), library share CRUD (Steps 6–9 share-list parts), timeline browse (Step 10), path/stack/live-photo redaction (Step 7), read-surface matrix (Step 5).
2. **Album provenance**: `album_asset.sourceLibraryId`, the reusable predicate on every §2 read surface, insertion precedence, `copyAlbums`, shared-link guards, sync-stream exclusion.
3. **Editor metadata**: `sidecarWriteProperties` split, the transactional metadata primitive, extraction changes, editor endpoints for metadata only.
4. **Person/face editing + role-aware web UI**: the remaining curation endpoints and the web editor surfaces (Steps 12–14 finish here).

## 9. Open questions for the product owner (non-blocking; defaults chosen)

1. Should **admins** see/manage every library's share list in the admin UI? (Default v1: API allows admin; no admin UI built.)
2. Should sharing generate a notification for the recipient? (Default: no; they see it on the Sharing page.)
3. Does the product owner explicitly want to override the locked library-authoritative album policy with independent durable grants? (Default v1: no; provenance enforces revocation and shared-link creation is excluded.)
4. Should an Editor ever be allowed to write XMP sidecars beside external originals? (Default v1: no; editor metadata is database-only/locked, and only the owner uses existing sidecar-writing workflows.)
5. Should an Editor be allowed to rename a person whose identity also appears outside the shared library? (Default v1: no, because that changes account-wide person metadata; the owner must perform that rename.)
6. Should **admins** be able to curate (edit metadata/faces on) other users' library assets, or only manage share lists? (Default v1: share-list management only — current admin status does not bypass owner-only `AssetUpdate`, and the editor service has no admin branch.)
